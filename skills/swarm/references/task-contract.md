# Compact task contract

Aim for 120 words or less. Use only the lines that carry a current decision,
boundary, or proof obligation; link source material instead of pasting history,
doctrine, or a crew map. Exceed the target only when required to preserve a
material safety, authority, or outcome constraint.

```text
<role-icon>ROLE - artifact name

Surface: user-visible host task; parent task title/ID. In Codex, use a Codex task.
Execution: active usage profile; resolved role model/reasoning; requested tier.
Goal: MOTHER, LEAD, or persistent ARCHITECT must inspect and continue a matching
active durable goal, create one if absent, or stop and escalate a conflict;
include objective, stopping condition, authority boundary, and required proof.
Finite roles do not inherit durable goal ownership.
Portfolio outcome: full user result this artifact must preserve.
Outcome/FUA: one inspectable user-relevant artifact.
Non-negotiables: exact must-haves this lane may not redefine.
Integration-ready: exact revision/artifact, composition instructions, required
proof states, and no undisclosed missing dependency.
Owns: exact mutable paths or external authority; prior owner release when transferred.
Deploy lane: for LEAD only, provider target, mutation surface, rollback receipt,
production-proof obligation, and required MOTHER lease when shared.
Boundaries: collisions and authority limits, never a hidden scope cut.
Input: exact revision and essential sources.
Execute first: first artifact-producing action; exact non-mutating surface receipt when consequential.
Heartbeat: active-since source and one-sentence material status; passive reads
only. MOTHER reads every active descendant, including grandchildren, and reports
state, material artifact/proof/integration delta, duration, blocker, and unblock.
Stall means configured owner updates without material change, not silence. Use
exactly one bounded same-surface recovery; if unchanged, return the exact
blocker and release/reassign under existing authority.
Done/proof: observable completion and claim-matched checks.
Visual proof: composed responsive render at supplied-reference and required
viewports/states, when visual or interaction output is in scope.
Review route: reviewer or accepting task title/ID.
SUBTASK/ASSIST: for a DOER, bounded independent SUBTASKs and child capacity, or
the concrete dependency/collision reason not to delegate.
System: ARCHITECT system interface for a LEAD impact, when relevant; ADVISOR may
answer one focused question then exits; neither has artifact/control authority.
On stall: configured recovery budget, then exact blocker and release.
Stop/handoff: terminal condition, accepting route, and immediate successor/unblock when deferred.
Peer handoff: immutable artifact identity; direct routine recipient; LEAD/MOTHER
escalation only for the defined authority boundary.
```

The template is a selection guide, not a form. Always preserve the outcome,
ownership, boundaries, proof, and terminal handoff; omit other lines when they
add no useful control. Add spend, viewport, rollback, or serial-handoff
constraints only when relevant. Do not prescribe an unrequested implementation
choice.

A lane-local passing test or approval is not integration-ready on its own. The
handoff must let its parent compose the artifact without rediscovery and must
label every required-but-missing proof `UNVERIFIED`. A visual lane cannot hand
back an accepted or deployable result without the composed render comparison;
if capture, a supplied reference, or a required viewport is unavailable, return
the exact blocker and `UNVERIFIED` proof state instead.

Ready for review stops active work and frees capacity, but the owner remains the
mutable correction route until acceptance, explicit transfer, or exact blocker.
Before any transfer, the old owner stops and releases, MOTHER records it in the
existing receipt, and the new owner acknowledges it; uncertainty stays
read-only. If the accepting route cannot receive a terminal handoff, try once,
take one liveness snapshot, then send the unchanged immutable handoff to the
nearest live ancestor or user and release. Never self-accept.

Before sending, verify that the task:

- fits no active owner;
- produces a concrete outcome rather than speculative reuse;
- cannot collide with another mutable owner;
- invents no product behavior or acceptance threshold;
- preserves portfolio non-negotiables and requested consequential capabilities;
- is a user-visible host task when it represents a RUSH portfolio lane;
- uses the configured role model and reasoning when the host supports and
  permits saved-config selection, or when its required direct request exists;
- starts with exactly one configured role emoji and uses MOTHER, LEAD, or a
  concise contextual task role at the correct hierarchy level, with
  no separator between the emoji and that role;
- uses one familiar role word when possible and a short concrete artifact;
  prefer fewer characters when the result stays clear and obvious, but keep a
  longer label when it is the most accurate familiar term;
- does not substitute a subagent for a required Codex task;
- has an event-driven review return and terminal handoff instead of polling or
  waiting without an escalation route.

DOER owns one bounded task artifact and may create or receive temporary wildcard
DOER ASSISTs to execute independent SUBTASKs. When two or more independent
SUBTASKs and child capacity exist, it delegates promptly; otherwise it records
the concrete dependency or collision reason. On a material issue, clog, or
missed explicit checkpoint/deadline, it invokes a bounded diagnostic or execution
ASSIST slice. ASSIST may perform any bounded developer, design, research,
operations, or proof function within scope, but
returns evidence/output only to its hiring MOTHER, ARCHITECT, LEAD, or DOER and
cannot independently review, self-accept, integrate, mutate providers, deploy,
or create another authority layer. ARCHITECT persists system coherence and supplies concise
dependency/decision interfaces to affected LEADs; ADVISOR answers one focused
question and exits. Neither owns an artifact, builds, schedules WORKERS, reviews,
integrates, mutates providers, or deploys; MOTHER receives only escalations and
lane receipts.

The handoff returns the artifact, proof, unresolved P0-P2 issues, claim limits,
and accepting owner. It does not self-accept.

MOTHER contracts name orchestration only: MOTHER never edits. Every integration,
collision, implementation, asset-generation, or task-level proof artifact has a
named DOER/TASK owner and acceptance route.

A deployable LEAD contract owns the lane end-to-end: DOER decomposition and
integration, immutable integration SHA, independent REVIEW route, correction
loop, lane acceptance, provider/deploy controls, rollback receipt, and production
proof. LEAD submits the exact integration SHA to REVIEW and deploys only that
independently approved SHA; it never reviews or self-approves its own work. It may deploy concurrently
only when its provider target/surface is disjoint. For a shared target, MOTHER
records and grants the release lease before mutation; LEAD returns it after the
rollback/production-proof obligation reaches its terminal state.

## Provisioning receipt

If creation returns only a provisioning handle, take one bounded inventory or
host-supported setup observation. A handle is setup evidence, not delegation.
Without a materialized task ID or host resolver, classify it as unmaterialized
setup failure: it has no owner, consumes no capacity, and cannot block a
duplicate retry. Preserve the handle only as diagnostic evidence, then spend the
configured recovery budget on one representative canary retry through a real
user-visible host task surface, preferably removing a suspect optional setup
parameter without changing the artifact contract. Fan out only after a real task
ID starts material work. While setup is unresolved, MOTHER may order immediate
safety containment only; all non-emergency artifact work remains delegated and
must not be absorbed into MOTHER or hidden work. If the canary also remains
unmaterialized, stop creation and report the exact host setup blocker.
