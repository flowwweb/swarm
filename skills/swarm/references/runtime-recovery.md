# Recovery from failures and mistaken assumptions

Applies to every SWARM structural role and profession. Run this loop when a
failure lacks a clear cause, evidence contradicts a blocker, permission is
uncertain, a tool times out, or the same tactic or explanation repeats without
progress. A user correction triggers reassessment immediately. Recovery changes
the next decision; it never resets the user's objective, history, or authority.

## Reassess once, then act

1. **Capture the failure.** Record the exact action, target, current environment,
   returned error and exit/completion state. Separate observed facts, inference,
   and unknowns. A reported rejection without its original receipt is unverified.
   For uncertain writes, inspect the target before retrying; preserve dirty work
   and account for partial effects.
2. **Rebind the task.** Read the latest user correction, unsuperseded authority,
   applicable higher-priority rules, current tool capabilities, literal checkout
   and owned surface. Name the source and scope of any claimed restriction.
   Carry forward existing authorization; ask again only for a genuinely new
   reserved decision. Unrestricted filesystem access does not waive an actual
   command-specific denial, destructive-action requirement, or protected target.
3. **Test the assumption.** State the disputed claim and choose the smallest
   authorized, preferably read-only probe that could disprove it. Distinguish
   command syntax, tool transport, filesystem access, disk capacity, provider
   authentication, and policy denial. One failed command establishes failure of
   that attempt, not every tool, target, provider, or task. Verify the intended
   surface directly; a working browser login and broken browser control can
   coexist. If the cause remains unknown, say so and narrow the affected scope.
4. **Choose a different next action.** Correct invalid syntax or inputs, use an
   already-authorized capability for an ordinary execution failure, or continue
   an independent owned deliverable. State what changed and why it should help.
   Honor the existing typed retry budget; changing wording, shells, or parameters
   without new evidence is the same tactic. An explicit policy denial is not an
   invitation to route the same prohibited operation through another tool.
5. **Verify and correct the record.** Check the intended result and partial
   effects, retract any disproved blocker, and resume the original objective.
   A successful probe proves only its scope. For cleanup, success requires the
   exact authorized target's post-state and measured free space; a command exit
   or a revised explanation does not prove reclaimed bytes.

Complete this loop with either a verified advance or an exact remaining blocker
and its release condition. Do not end with another plan when an authorized next
action is available. Keep unaffected owned work moving.

## When the same confusion survives

After one bounded reassessment fails, send the existing accountable parent or
independent reviewer a compact packet: objective, authority source, exact error,
facts versus discarded assumptions, partial effects, attempted route, remaining
permitted routes, and one falsifiable next question. Reorient the same owner;
preserve user-selected model, reasoning, worktree and role unless explicitly
authorized otherwise. No replacement CTRL, new recovery role, or recursive
review chain is created. If review is unavailable, retain that narrow gap and
continue any independent authorized action.

Use the existing retry-topology ledger and task handoff for material recovery
decisions; do not add a second log, scheduler, polling loop, or state machine.
Receipts contain safe error codes and evidence references, not secrets or raw
prompts. Existing runtime exhaustion rules decide terminal BLOCKED; repeated
narration or elapsed time is not exhaustion. Keep a genuine safety or user-only
gate scoped to the affected operation and name who or what can release it.

For example: an authorized disk cleanup command is rejected, with no confirmed
post-state. The facts are that this attempt failed and reclaimed space is
unverified. Check the exact rejection and target, then inspect other authorized
targets read-only. Continue only a permitted route; neither assume all cleanup
is forbidden nor bypass the rejection by repackaging the same denied deletion.

## Authorized local access recovery

For the SWARM config loader, another required read-only internal helper, or
another already-authorized safe local action, apply this narrower rule.

Use the requested runtime when it is allowed. An ordinary local filesystem or
executable permission failure is not yet a terminal blocker. The eligible owner
requests supported sandbox or access approval once for the exact authorized
action and target before recording host-gate fallback or a blocker. Explain the
observed access error and requested scope. CTRL coordinates and relays this;
it never executes the producer's action or takes over the task.

Pending approval waits; do not cancel the request, repeat it, count waiting as
route exhaustion, or report a terminal blocker. Reconcile interrupted turns and
uncertain writes before retrying. Once access is approved, retry the exact action
through that supported route and verify its result. Keep unaffected owned work
moving while the affected operation waits.

An actual policy or automatic-review denial remains binding. Retain the exact
action, decision source and stated reason; do not resubmit the denied action
through another tool or runtime. No blind privileged execution, ACL changes,
credential reset, approval bypass or repeated permission loop is permitted.
If supported access approval is unavailable, record that exact capability gap;
do not invent an approval decision.

Local access, disk capacity, tool transport and provider authentication are
separate causes; use the observed error to choose their existing recovery route.
A disk-full, transport or credential error does not trigger access approval. A
blocked executable does not prove a provider is logged out, unhealthy, or
unauthorized. A provider session does not prove permission to launch a local
runtime. State only the receipt actually observed.

Only after the supported request is unavailable or actually denied may the owner
record a typed host-gate exception and consider a separately permitted fallback.
A pending request does not justify that exception. This recovery does not waive
approval for external or provider actions, destructive actions, or decisions
reserved to the user.

## Use one same-purpose fallback

For a required read-only helper, one already-authorized runtime is eligible only
with a current-host receipt, such as a bundled workspace dependency receipt or
a successful non-mutating capability check, and only when its use does not bypass
an actual denial. Do not infer access from a provider login, an unrelated command,
an older task or the runtime merely existing on disk.

Retry once with that authorized runtime, without changing
the script, config path, arguments, read-only purpose, provider state, or safety
boundary. Do not cycle through interpreters, shells, browsers, credentials, or
providers. Do not launch privileged execution outside the supported approval
route. If the fallback works, report which runtime executed without
claiming broader approval or provider access.

## Contain only the affected actions

If the loader still fails, report the exact tooling or environment error and
pause new scheduling plus actions whose correctness depends on unresolved
config. Already-owned safe work, proof, review, and handoffs that do not require
new config resolution continue. Do not apply silent defaults, interrupt proven
unaffected owners, or generalize the loader failure into an account or provider
failure.
